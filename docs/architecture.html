Engineering notes

How Rihla works

Rihla plans complete multi-day itineraries — at most five days, UAE only — around the events already on your calendar. This is a walkthrough of every file, what it does, and why the numbers inside it are the numbers they are.

351seeded places

~5.3klines of Python
~2.4klines of TS/TSX

One idea governs the whole system: the language model never builds the itinerary. It reads intent from chat and calls tools; a deterministic Python planner assembles and validates the schedule. That split is what makes the output testable — you can run a thousand random party profiles through the planner and assert the validator always passes, which you cannot do with a model.

The shape

A React workspace on the left of the screen talks to a FastAPI backend. SQLite is the source of truth; ChromaDB holds embeddings for semantic search only, and is never authoritative.

React + TypeScript (Vite) FastAPI ├─ ChatPanel the only way to plan ├─ orchestrator.py OpenAI function calling ├─ MapView react-leaflet ├─ planner.py deterministic, pure ├─ ItineraryStrip day tabs → slot cards ├─ validator.py constraint checker + repair ├─ SlotEditor replace/adjust/remove ├─ retrieval.py Chroma → SQL filters └─ BudgetPanel server-computed only ├─ travel.py ORS → cache → haversine ├─ budget.py age-tier pricing ├─ memory.py per-user Chroma memory └─ repo.py the scoping choke point SQLite (truth) + ChromaDB (semantic)
Load-bearing decision

repo.py is the only module that queries user-owned tables. Every function takes user_id from the auth dependency, cross-user access returns 404 rather than 403 — a 403 would confirm the row exists — and asking it for a shared table raises TypeError. A choke point only works if going around it is awkward and misusing it fails loudly.

Build order

These phases are a real sequence — each depends on the one before — which is why they are numbered here and nothing else in this document is.

  1. Schema, auth, scoping, seed data Auth first, so every later router is written user-scoped from the start rather than retrofitted.
  2. Planner engine and validator Written test-first and kept pure — no database session, no HTTP client, no clock.
  3. Travel provider, budget allocator, itinerary API OpenRouteService with a shared cache and a silent haversine fallback.
  4. Chat orchestration, threads, Chroma memory Tools that write only the calling user's rows, and per-plan chat threads with unread state.
  5. The workspace UI Built to the Claude Design mock: thread rail, map, itinerary strip, pinned budget bar.
  6. Web search adapter and docs Optional garnish for live one-off events; fails silently to seeded data.
  7. Catalog expansion and facet columns 164 → 351 places, richer descriptions, and the facets the planner filters on promoted to real columns.

Database tables

Eleven tables. Two are shared and deliberately have no user_id — the places catalog is the same for everyone, and place-to-place travel is user-agnostic so one cache benefits all users. Everything else is per-user.

Why one places table and not one per type

A category column discriminates twelve kinds — park, waterpark, theme park, museum, aquarium, beach, adventure, casual dining, fine dining, mall, show, cruise — and the planner treats every one identically. It needs coordinates, price bands, hours, min_age, duration and three fit scores; nothing else. Splitting into restaurants / parks / beaches would force a polymorphic foreign key from slots, UNION queries in retrieval and per-type branches in scoring, for no gain.

Genuinely type-specific attributes live in the tags JSON array. The three the planner needs to filter on were promoted to real columns, because free text cannot be queried:

ColumnTypeWhat it changes
indoorboolA summer midday prefers somewhere air-conditioned.
booking_requiredboolSurfaced up front rather than discovered at the door.
closed_monthsint[]A correctness filter — the venue is shut.
price_bandsJSONAge-tier pricing, checked in order.
Why a month list, not a boolean

Global Village runs October to April; Miracle Garden November to May. A boolean seasonal flag could only ever produce a warning. A list of closed months lets the planner refuse to schedule into a shut venue at all — seventeen places carry one, and an August plan books none of them.

Age-tier pricing

Most UAE venues charge a child rate for 3–12 and an adult rate above that, but plenty differ. price_bands is checked in order, and falls back to the flat child/adult split when absent: 

[{"max_age": 2,    "price": 0},     // infants free
 {"max_age": 12,   "price": 155},   // child rate
 {"max_age": null, "price": 199}]   // everyone else

This is what makes a 13-year-old correctly pay the adult rate, and what decides whether the "1 child free (under 3)" chip appears on a slot card at all.

A subtle trap

schemas.py uses import datetime as dt rather than from datetime import date. With from __future__ import annotations, a field named date shadows the type date in every later annotation, and date | None resolves to None | None — a TypeError at import.

The planner in depth

planner.py has no database session, no HTTP client and no clock. Travel arrives as travel_fn(from_lat, from_lng, to_lat, to_lng) -> TravelInfo. That purity is what makes running hundreds of property-test examples cheap enough to do on every commit.

The party profile

Weights come from the party, never from the model. Four branches, chosen in order:

PartyWeightsDay shape
Anniversary, adults only romance 1.0 11:00–23:30, 3h slots, evening-biased, fine dining after 17:00
Any child under 8 kid 1.0 09:00–19:30, 2h slots, midday rest, early dinner
Children, none under 8 teen 1.0 09:30–22:00, 5h slots, no rest
Adults, other occasion teen 0.6 · romance 0.5 09:30–22:30, 4h slots

A worked example

Two adults, children aged 7 and 13, Abu Dhabi start, three days, AED 3,500, in August:

1. retrieve 351 places → within 140 km of start → 229 → Chroma similarity on "young children, animals, gentle indoor" → category-capped shortlist of 80 + 14 cheapest reserved 3. cluster 3 geographic buckets, nearest-to-home first each topped up to ≥3 restaurants 4. assemble day 1, cursor 09:00 09:20 Al Bateen Beach (free, kid_score 0.88) 11:35 Galleria Al Maryah (indoor — it is 40 °C outside) 13:17 Shakespeare and Co (lunch window is due; rest yields to it) 15:40 Louvre Abu Dhabi (indoor, under-18s free) 18:02 Beirut Restaurant (dinner window) 5. route 10 chosen legs sent to OpenRouteService; the other ~800 candidate comparisons never left the process 6. validate no overlaps · travel honoured · venues open · ages clear · ≤ cap → AED 3,481 of 3,500

Each candidate is re-ranked from the current position at every step, so the next stop is a good place that is also nearby: 

score(place)
  − 0.012 × km_from_current_position     # proximity penalty
  + 0.35  if hot_midday and place.indoor # summer heat bonus

Preferences & memory

Preferences have two origins, and the difference matters. A stated preference comes from the user saying so. A slot_edit preference is inferred from behaviour — you swapped a stop out — and is only recorded after you confirm it, via the dark toast that appears under the edited card.

You replace a stop └─ PATCH /itineraries/{id}/slots/{slot_id} └─ toast: "Avoid adventure in future plans?" ← never written until answered ├─ Yes → preferences(kind=dislike, source=slot_edit, strength=0.7) │ └─ MemoryService.remember_preference → Chroma, tagged user_id └─ No → nothing recorded at all

How a preference changes a plan

preference_signal() matches a preference against a place by category, or by any word longer than three characters appearing in its name, category or tags. The signal is then folded into the score: 

signal += strength                # a like
signal -= strength × 1.4          # a dislike

score = w_semantic·similarity + profile_fit + 0.45 × signal
Asymmetry on purpose

A dislike is weighted 1.4× harder than an equal-strength like. Avoiding a stop someone will hate matters more than including one more they will merely enjoy — a bad slot ruins an afternoon, a missing good one does not.

The isolation guarantee

MemoryService is constructed with a user_id and is the only module that touches the preference_memory collection. Every query carries where={"user_id": ...}, injected once, in one place — an unfiltered cross-user read is not expressible from a route handler.

Document ids are namespaced u{user}-pref-{id} so two users' rows cannot collide, and recall re-checks the returned metadata anyway. That check should be unreachable; a leak here would be a privacy bug, so it is verified rather than trusted.

Never authoritative

Chroma is an accelerator. If embeddings are unavailable, recall() falls back to the user's own strongest SQL rows and the product carries on. SQLite is always the source of truth.

One meal category exception

The "avoid this in future" prompt is suppressed for dining categories. The planner has to schedule lunch and dinner, so "avoid dining in future plans" is advice it could never act on.

Retrieval & vectors

Two Chroma collections: places (shared, no user filter by design) and preference_memory (per-user, always filtered). Both are embedded with text-embedding-3-small.

What gets embedded per place is deliberate:

f"{name}. {description} Tags: {tags}. "
f"Category: {category}. Located in {emirate}. "
f"{'indoor and air-conditioned. ' if indoor else ''}"

The facets are spelled out in words rather than left as booleans, because that is what a query like "somewhere indoors for the afternoon" actually matches against.

Why descriptions were rewritten

The original catalog averaged 96-character descriptions. Every one was rewritten to ~223 characters, naming who a place suits, what it feels like and when to go. Short text embeds weakly; this was the single largest lever on retrieval quality, and it improved the original entries as much as the new ones.

The pipeline, in order:

1. SQL hard filters min_age ≤ youngest attendee, optional emirate and price 2. Trip radius ≤ 140 km from start — applied BEFORE shortlisting 3. Semantic query Chroma top-200 by cosine similarity 4. Category spread ≤ 13 per category, so 80 aquariums cannot crowd out meals 5. Budget relief cheapest 4 dining + 10 other, added back regardless of rank
Order matters

Steps 2 and 3 used to be reversed. Shortlisting before filtering meant the 80 slots were spent on places two hours away, and a day could end up with no reachable lunch at all. The planner also enforces a radius — but by then the shortlist has already been chosen.

Travel times

Three layers, tried in order: OpenRouteService for a real route, the shared cache for a pair already looked up, and haversine as a floor that never fails. 

road_km  = straight_line × 1.3
speed    = 90 km/h if straight_line > 40 km else 45 km/h
minutes  = road_km / speed × 60 + 10        # parking buffer
cost     = road_km × 2.5                    # AED, its own budget line

A fallback leg is marked estimated=true, which the UI renders as "~35 min" with a dashed polyline. The map is honest about what it does not know.

Estimates are never cached

Only real routes are written to travel_cache. Caching a guess would freeze it in place and stop a later successful ORS call from ever improving on it.

Two callables, one service

The planner asks "how far is this one?" for every candidate at every step — hundreds of pairs per trip, of which a dozen survive. Routing all of them exhausted the free tier's 40-requests-per-minute limit, and most segments came back rate-limited.

  • estimate_fn() — network-free haversine, used for ranking. Relative distance is all a comparison needs.
  • travel_fn(places) — real routing, used only for the legs actually chosen, then re-validated because a real route is usually slower than the estimate.

One three-day plan went from several hundred API calls to about ten.

Chat orchestration

The orchestrator is constructed with the authenticated user, loads that user's family, preferences and vector memory into its system context, and exposes six tools. No tool schema contains a user_id parameter — the model cannot address another user however it is prompted, and a test asserts exactly that.

ToolEffect
save_family_detailsReplaces family_members, records likes and dislikes.
create_eventAdds a calendar entry. Idempotent on (user, title, date).
get_upcoming_eventsPowers "what events are upcoming?" and the offer to plan.
generate_itineraryCalls the deterministic planner. Refused if intake is incomplete.
get_itineraryReads current plan state. beyond spec

Why get_itinerary exists

The five specified tools can all create or change things; none could read a plan back. Asked to summarise, the model could only describe whatever a previous tool result left in its context — which goes stale the moment a slot is edited. It reported a total of AED 2,127 while the budget bar beside it read AED 1,560. The system prompt now forbids quoting a figure from memory.

Streaming

POST /chat emits typed SSE frames: conversation, token, tool, tool_done, intake_required, itinerary_updated, budget_updated, error, done. The right pane re-renders while the assistant is still talking.

The browser reads this with fetch and a ReadableStream, not EventSource — EventSource cannot send an Authorization header.

Tool calls render as activity rows with their inputs, phrased server-side because the server already knows what the arguments mean: 

✓ Checking your calendar   next 60 days           3 events
✓ Building your itinerary  3 days · AED 2,500     AED 1,574 of AED 2,500
✓ Noting a preference      dislikes long queues   noted

One stacking rule worth remembering

Leaflet gives its panes and controls z-indexes up to 1000. Without z-index: 0; isolation: isolate on the map container, those compete directly with the app's popovers — and the map paints straight over the slot editor, which is correctly positioned the whole time and simply invisible.

Two traps the suite itself fell into

It wrote to the real database. get_settings() is lru_cached and pytest imports test modules before session fixtures run, so a scope="session" override landed too late. Fixed at conftest module scope, with an assertion guarding the regression.

It made billable API calls. conftest popped the keys from os.environ — but Settings also reads backend/.env, and an absent variable does not override a value present in a file. They are now blanked, and a fixture fails loudly if any key is live during a run.

Bugs worth knowing

These are recorded because each one was invisible until something specific exposed it.

The nap instead of lunch

For a family with a child under 8, the midday rest fired at 13:00 and pushed the cursor past the 14:00 lunch window, which then counted as missed. They got a rest instead of lunch, every single day. Teen plans had six meals; the same catalog gave a young family one. A due meal now takes precedence over the rest.

Meals priced out of existence

One expensive anchor — Ski Dubai at AED 1,341 — consumed the day's envelope, so every meal window then failed its affordability check. Budget is now reserved for the meals still ahead before any non-dining slot is accepted.

Slot ids that moved

persist_plan deleted and reinserted rows, so removing slot 2 renumbered the survivors into ids 1, 2, 3 — and the client's selectedSlotId then pointed at a different slot. Rows are now updated in place via a row_id carried on the planner's dataclass.

A label that contradicted the app

The tool trace read "Reading the current plan → no plan yet" while the assistant correctly quoted AED 1,559.98 beside it. The summariser tested result.get("itinerary"), but the populated shape carries itinerary_id and no "itinerary" key at all — so every successful read was labelled as an empty one. Making the assistant's work visible is what surfaced it.

Known limits

  • The map is real geography, not the illustration. MapTiler tiles are recoloured toward the design's cream and teal, but tiles cannot reproduce hand-drawn road ribbons or lettering.
  • Prayer times are approximate. A static monthly UAE table, ±10 minutes — well inside the slack of a 20-minute gap.
  • Place photos are placeholders. image_url is seeded null and cards render a per-category illustration, so a card can never show a broken image.
  • Some coordinates are unroutable. ORS returns 404 for a few beach and island points with no road access; those legs fall back to dashed estimates by design.
  • The assistant is a hard dependency. The scripted no-LLM fallback was built and then removed by decision, on the basis that the key will always be present. This drops the spec's foolproof guarantee, and is recorded rather than left as a silent contradiction.
  • Prices and hours are plausible, not authoritative. Coordinates are real so routing is genuine; the figures are illustrative.
